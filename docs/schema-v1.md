# Binary schema contract

The Go library implements v1 schema compilation. The CLI exposes schema validation, decoding, encoding and inspection. The Go library also implements decoding, inspection and encoding; this release implements schema version 1. UTF-8 JSON schema files have no BOM, no duplicate or unknown members, nulls, trailing documents, fractional/exponent dimensions or invalid Unicode. Limits apply before allocating from untrusted lengths. Identity is SHA-256 of the exact validated file bytes, including whitespace and trailing newline. V1 performs no schema canonicalization; resaving a schema changes its identity and requires decoding again.

Root members are exactly schema_version (integer 1), name (identifier), endian (little or big) and fields (ordered array). Identifiers use ASCII [A-Za-z_][A-Za-z0-9_]{0,63}; names are unique in each object. Every field has name and type. Integer types are u8/u16/u32/u64/i8/i16/i32/i64, with two's-complement signed representation. A per-integer endian may override the root; otherwise it inherits the root, including inside arrays. There are no floating-point, bit-level, offset/seek, recursive, imported or executable types in v1.

Since EByte 0.2.0 a field may have type repeat with until and fields. It repeats an element object, like an array without a count, and has no count, length, encoding or expect. until is end_of_input or tag_mismatch. end_of_input is allowed only on the last root field without when; elements continue while at least one input byte remains. tag_mismatch requires the first element field to be an unconditional bytes field with a literal length from 1 to 16 and an expect value, the tag; elements continue while the next input bytes equal the tag, and the repeat ends at the first position where they don't, including end of input or fewer remaining bytes than the tag. Up to 16 bytes are looked at ahead and then read normally by the following fields. An element must consume at least one byte. Repeat elements follow array scope rules for references, conditions and depth; count_of cannot target a repeat. The element ceiling is the array ceiling.

A bytes field requires length, a nonnegative integer byte count, or {"field":"earlier_integer"}. Its document value is lowercase hex, two characters per byte. A string requires length in the same forms and encoding ascii or utf8. Length counts encoded bytes, not runes. Strings are exact-width: no implicit trimming, termination, normalization or padding. NUL and spaces remain literal characters in JSON; invalid encoding fails. A zero length is legal. Padding, terminators and reserved bytes must be declared as ordinary fields and preserved explicitly.

An array requires count in the same literal/earlier-integer forms and fields defining an object per element. It has no length property or encoding. Nested arrays are allowed within bounded depth. A reference always names an earlier unconditional integer sibling in the same object, never a parent/other element. Dynamic negative counts/lengths fail before reading/allocating the field. Integer values cannot exceed their declared type. No arithmetic, dotted references or expressions are accepted.

An integer or bytes field may have expect: a canonical decimal string in its integer range, or lowercase hex exactly matching a literal byte length. Other types and dynamic-length byte assertions are excluded in v1. A mismatch fails at the first differing byte for byte literals; integer mismatch points to the integer's start. Assertions validate bytes; encoding must also satisfy them rather than silently correcting user values.

Any non-derived field may have when: {"field":"earlier_integer","equals":"canonical_decimal"}. The referenced sibling is unconditional and the literal must fit its type. Equality is the only predicate; a flags byte equal to 1 is not a bit-mask test. A false condition consumes no bytes and requires that field to be absent in the document. References to conditional fields are invalid even if a particular input would make them present. Array element fields follow the same scope rules independently.

An unconditional unsigned integer may instead have derive: {"count_of":"later_array"}. The target is one later unconditional sibling array whose count is exactly {"field":"this_integer"}. Only that recognized count binding may look forward (0.3.0 adds driving size_of and measured derives, below); there are no general forward dependencies or cycles. Derived counts cannot have expect or when. Decode uses the stored count to read the array, exposes its observed value in the trace and omits it from editable values. Encode calculates the count from the supplied array before writing either field, checks representability, and refuses a user-supplied derived value. Ordinary stored count fields remain editable and must agree with their arrays; the encoder never guesses which contradictory value to trust. A count field may not drive another length/array when it is derived.

Since EByte 0.3.0 derive has more forms, each an object with exactly one of count_of, size_of or offset_of, plus an optional add only where stated. A derived integer is always unsigned, unconditional and without expect, is omitted from editable values and appears in the trace with its stored value.

Driving forms are calculated before the fields they drive. {"count_of":"later_array"} is the form above. {"size_of":"later_field"} is driving when the target is a later unconditional bytes or string sibling whose length is exactly {"field":"this_integer"}; encode writes the target's byte length (hex characters / 2 for bytes, UTF-8 bytes for strings). A driving integer drives exactly one dimension, and later siblings may use it in when.

Measured forms describe positions and sizes and drive nothing. {"size_of":"sibling"} with any other target is that sibling's encoded byte length; a target whose length or count references the derived integer is never measured, so size_of an array counted by this integer is invalid. {"size_of":{"from":"a","to":"b"}} is the byte length from the start of sibling a through the end of sibling b, inclusive, with a not after b; the range may include the derived integer itself. {"offset_of":"sibling"} is the sibling's absolute byte offset from the start of the input. {"count_of":"repeat_sibling"} is the number of elements in a repeat. Targets are siblings in the same object, earlier or later, of any type; an absent conditional sibling has zero length at the position where it would start. add is a canonical decimal string in the int64 range, possibly negative, added to the measured value. No length, count or when may reference a measured integer, so its value never changes how input is read.

Decode reads a measured integer like any other and, once its object is complete, compares the stored value with the measured one; a difference is constraint_mismatch at that integer, so files with a stale size or offset fail instead of round-tripping silently. Encode writes a zero of the same width in its place, finishes the object, then writes the measured value; a result that is negative or does not fit the type is value_out_of_range. Measured values never change field widths, so writing them moves nothing. Sizes are byte counts of encoded fields; there is still no other arithmetic, no multiplication and no reference outside the object.

Since EByte 0.4.0 derive may instead be {"checksum":"algorithm","of":target}, where target is one sibling name or {"from":"a","to":"b"} as for size_of. It is a measured form without add. The algorithms are crc32 (IEEE 802.3, as in PNG, ZIP and gzip; check value cbf43926 for the ASCII bytes 123456789), adler32 (zlib; 091e01de), crc16_arc (reflected 0x8005, initial 0; bb3d), crc16_modbus (reflected 0x8005, initial ffff; 4b37) and crc16_xmodem (0x1021, initial 0; 31c3). The integer must be exactly u32 for crc32 and adler32 and u16 for the CRC-16 variants; its own endian decides the byte order. The checked bytes are the encoded bytes of the range, including any other measured integers in it; the range may not contain the checksum itself or another checksum sibling. Decode hashes the range while reading it and reports checksum_mismatch at the checksum integer when the stored value differs. Encode writes checksums after every other measured integer of the same object, so sizes and offsets inside the range are final; a range may contain arrays, repeats and nested objects with checksums of their own, which are written first because inner objects are finished before their parent. A checksum covers bytes exactly as stored: a checksum over decompressed data, such as a ZIP CRC-32 of a deflated file, is outside what a schema can declare.

Resource ceilings for v1 are schema bytes 1 MiB, 1024 total schema field declarations, schema/array nesting 8, binary input/output 16 MiB, one byte/string field 16 MiB, one array 65536 elements, 100000 value nodes and independently 100000 trace entries and 64 MiB serialized document or trace JSON. These are upper bounds, not throughput promises. Library options may lower them; never silently raise them. Count/product/addition arithmetic is checked before reading, allocating or writing. JSON escape expansion and hex expansion count toward output budgets. The CLI has no unbounded mode. Cancellation and reader/writer errors remain distinct failures.

The library exposes Compile(schemaBytes, limits), then Decode(ctx, io.Reader), LoadDocument(ctx, rawJSON), Encode(ctx, document, io.Writer) and Inspect using the same execution plan. These APIs are implemented. Readers need no seeking. Decoding materializes bounded editable values; no constant-memory promise applies to JSON. Encoding to io.Writer can leave partial bytes on failure. CLI encode will stage its output and publish without replacing an existing destination only on platforms whose publication behavior is verified before release.

Depth counts nested array and repeat field scopes: root fields are depth 0; entering an array element's fields adds 1, so an array nested in seven enclosing arrays has element scope depth 8 and is allowed. A ninth nested array is rejected even when its count would be zero. Element objects do not add another level. Schema field declarations count every field once in all nested fields lists, not multiplied by runtime array counts. A value node is the values root object, each active non-derived scalar, each array or repeat container and each element object; absent/derived fields add no value node. A trace entry counts every emitted preorder entry including root, derived integers, containers and failed nodes. The 100000 budgets are separate per output, never pooled; both must be checked before adding a node. Metadata envelope members are fixed overhead excluded from node counts but included in the separate 64 MiB serialized-size ceilings. Parent trace entries are counted once and updated in place on failure. These budgets cannot authorize reading beyond the input/output byte ceilings.

The Go library now implements schema compilation through Compile(schemaBytes, limits), DefaultLimits(), and immutable Plan metadata accessors Name(), SchemaSHA256(), and Limits(). Decode, Inspect and Encode execute the compiled plan, and LoadDocument strictly validates editable JSON. Limits are exact ceilings: start with DefaultLimits() and lower values; zero does not select a default. Invalid negative or raised ceilings return schema-stage limit_exceeded. The schema byte ceiling bounds the temporary JSON tree before parsing; a separate JSON nesting safety ceiling of 40 protects syntax traversal. Unknown property diagnostics identify the containing object rather than echoing arbitrary member names.

Since EByte 0.6.0 there are three more representations.

Floats: types f32 and f64 are IEEE 754 binary32 and binary64 in the field's endian. Their document value is a string. Decode writes a finite value as the shortest decimal that reads back to the same bits (for example "1.5", "-0", "1e+30", "3.4028235e+38"), an infinity as "inf" or "-inf", and a NaN as "nan:" followed by all its bits in lowercase hex, 8 digits for f32 and 16 for f64 (for example "nan:7fc00000"), so every bit pattern round-trips. Encode accepts those forms and any decimal matching -?(0|[1-9][0-9]*)(\.[0-9]+)?([eE][+-]?[0-9]+)?, rounded to the nearest value with ties to even; a decimal that rounds to infinity is value_out_of_range, and a nan: value with the wrong width or bits that are not a NaN is invalid_document. Floats have no expect, when references, derive or dimension use, and the trace shows their value in the same form. Diff compares that form, so it compares bits.

Bit fields: type "bits" with "bits" from 1 to 64 is an unsigned integer packed with its neighbours. Consecutive bits fields form a group, which must add up to a whole number of bytes, at most 8, and must not be broken by any other field or by the end of the object. The group's bytes are read as one big-endian unsigned integer and members take their bits from the most significant end, in schema order; this is the network and most file-format convention, and other bit orders are not supported. Members are decimal strings like integers, may have expect and may be referenced by length, count and when like an unconditional integer; they may not have when or derive. In the trace each member has kind bits, the value it holds, and the offset and length of its whole group; a size, offset or checksum that names a member covers the whole group.

Forward jumps: a bytes field may have "length": {"until_offset": target}, where target is a nonnegative literal absolute offset or the name of an earlier unconditional integer or bits sibling. Its length is target minus the field's own absolute offset, so the field holds every byte up to the declared offset and the next field starts there. Nothing is skipped or discarded and input is still read forward only, so an offset behind the current position is constraint_mismatch at the field on decode. Encode writes the bytes it is given and requires their length to match the same calculation, reporting constraint_mismatch otherwise; it does not move the offset for you. A measured integer cannot be the target, because measured values never decide how input is read.
