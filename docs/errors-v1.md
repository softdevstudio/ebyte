# Diagnostics contract

The diagnostic has diagnostic_version 1, stage (schema/decode/encode/io), code, path, offset, field_start, expected and observed. Paths are JSON pointers. offset is a binary failure position when known, otherwise null; field_start is the affected field's start when known, otherwise null. Invalid schema/document JSON uses null binary locations; schema paths identify schema properties. All locations are nonnegative byte positions, not character indices.

Codes initially cover invalid_schema, invalid_document, schema_mismatch, constraint_mismatch, truncated_input, trailing_data, invalid_encoding, value_out_of_range, count_mismatch, limit_exceeded, cancelled, read_failed, write_failed and destination_exists. Error precedence follows execution order with schema validation before input reads and resource/range checks before allocation or consuming the affected field. A real reader error is read_failed, not EOF. Unexpected EOF in binary input is truncated_input; the CLI's schema and document JSON reads report a reader's unexpected EOF as read_failed. A short write with nil error is write_failed. Cancellation never becomes an apparent successful partial result.

For truncation, offset is the first unavailable byte (observed EOF position), field_start is the start of the incomplete field, expected describes its requested total length and observed describes available bytes. A root trailing byte has offset at the first extra byte and path "". Invalid string encoding points to the first invalid byte within the field. Byte literal mismatch points to its first differing byte; integer literal mismatch points to the field start. Range/count/limit failures during encode may have null locations until an output position is established. A trace's failed field length records only consumed bytes, even if constraint validation happened after reading the whole field.

expected/observed are bounded descriptions of at most 96 Unicode scalar values each, with JSON escaping on machine output. Describe lengths, ranges or condition kinds by default; do not dump source bytes, string values, filenames, schema literals or secret-bearing command arguments. No raw input preview is enabled in v1. Inspection of integer values is explicit inspect output rather than automatic error logging. An implementation must not falsely fill unknown offsets with zero. CLI exit 0 means the requested operation completed; 1 is runtime/I/O failure, 2 is usage/schema/document/representation validation failure, 3 is cancellation and 4 is a resource limit. The library implements schema/decode/encode/I/O diagnostics. Operational CLI commands implement these exits. Invalid command arguments use a static usage line on stderr with exit 2; operational failures emit a JSON diagnostic there.

Encoding assertion and ASCII failures use the known position in the prepared binary even though validation has not written bytes. Document parsing, identity, count and representation failures can have null locations. Invalid writer counts have unknown offsets; valid short counts identify the reported number of bytes written. Write failures explicitly warn that partial output may remain, and cancellation after a completed Write warns that output may already be written. The CLI publication helper reports destination_exists without replacing existing files or symlinks; cleanup failures warn that temporary staging files may remain, and post-link cleanup failures additionally warn that the destination may exist. Cleanup errors take precedence over an earlier operation error so they are not hidden. Concurrent cancellation retains those warnings and known locations.
